Sorting

With kit.js, data-kit-sort on the table makes the headers clickable: the first click sorts ascending, the second descending, the third restores the starting order. The header gets aria-sort (ascending, descending, none) and a button is placed inside it, so it also works from the keyboard. The column type is recognized from its content: numbers in the page language's format (in English 1,250.00, −310.00, 12 %, € 5; in Italian 1.250,00), dates (03/12/2026 in English, 12/03/2026 in Italian, 2026-03-12, with the time if present) and text, compared ignoring case and accents and with "natural" numbers (FT-9 before FT-10). Empty cells, or cells with just a dash, always go to the bottom; with equal values the starting order is kept. An aria-sort="ascending|descending" written in the HTML is the initial sort.

Several columns

With data-kit-sort="multi" you can also sort by several columns together: Shift + click or Ctrl/⌘ + click on the header adds it as the next criterion (and again reverses it, and then removes it), while a normal click starts over from that column alone. The first criterion is the main one, the others decide ties; with several criteria the priority number appears next to the arrow. From the keyboard, Shift + Enter on the header button. Try it: Customer, then Shift + click on Amount.

With Kit.table you can also sort from code (api.sort(2, "descending"), or api.sort([[2, "ascending"], [3, "descending"]]) with multi) and the kit:sort event arrives with { column, direction, criteria } (column and direction are those of the first criterion, criteria lists them all); see the API.

Text filter

data-kit-filter="#id" on a text field links the field to the table with that id: as you type, the rows that contain all the words remain (in any cell, ignoring case and accents). If nothing remains a "No results" row appears (data-kit-empty on the table to change the text). Sorting and filtering work together; the event is kit:filter with { query, count }.

Pagination

data-kit-page="N" on the table shows N rows at a time and adds the kit-pagination bar below: the count ("1–5 of 12"), the previous and next buttons and the page numbers with ellipses when there are many. The current page has aria-current="page", the count is an aria-live area and focus stays on the pressed button. It works together with sorting and filtering: changing either returns to the first page, and the count is that of the filtered rows. When printing the bar is not there and the page shown is printed.

With Django and htmx

When there are many records the server does pagination, sorting and filtering, one page at a time, and data-kit-sort, data-kit-filter and data-kit-page are not needed: they work on the rows already present. Only the CSS is used (kit-pagination, kit-sort-btn, aria-sort) and htmx replaces the block. If kit.js is present, fragments inserted by htmx initialize by themselves (htmx:load event): selects, comboboxes, tabs, highlighted code and sortable tables inside the response work without calling Kit.init.

The scheme: a container with an id (#invoices) that is the hx-target and holds the card with table and bar; the search field sits outside, so it is not replaced and the cursor stays where it is. hx-boost on the container turns normal links (headers, pages) into htmx requests with the browser history; the links keep working even without JavaScript.

The full page (invoices/list.html) contains the field and the container; the view responds with only the fragment (invoices/_table.html) to htmx requests.

# invoices/views.py
from django.core.paginator import Paginator
from django.db.models import Q
from django.shortcuts import render

ORDERINGS = {"date": "date", "customer": "customer__name", "amount": "amount"}

def invoices(request):
    qs = Invoice.objects.select_related("customer")
    q = request.GET.get("q", "").strip()
    if q:
        qs = qs.filter(Q(number__icontains=q) | Q(customer__name__icontains=q))
    sort = request.GET.get("sort", "-date")
    field = ORDERINGS.get(sort.lstrip("-"))
    if field:
        qs = qs.order_by(("-" if sort.startswith("-") else "") + field, "pk")   # "pk" keeps the order stable between pages
    page = Paginator(qs, 10).get_page(request.GET.get("page"))
    pages = list(page.paginator.get_elided_page_range(page.number, on_each_side=1, on_ends=1))
    # htmx asks for the fragment, but the "back" button with no cached history wants the full page
    partial = request.headers.get("HX-Request") and not request.headers.get("HX-History-Restore-Request")
    return render(request, "invoices/_table.html" if partial else "invoices/list.html",
                  {"page": page, "pages": pages, "q": q, "sort": sort})
/* while the request is in progress htmx puts .htmx-request on the hx-indicator element */
#invoices.htmx-request { opacity: .55; pointer-events: none; transition: opacity .2s; }

A few details that matter: {% querystring %} (Django 5.1) keeps the other URL parameters, so search and sort stay while changing page, and page=None removes the page when the sort changes; before 5.1 you need an equivalent template tag. The ids on the previous and next links are for htmx, which after the swap puts focus back on the element with the same id: keyboard users do not lose it. For headers, kit-sort-btn also works on an <a>; with multi-column sorting written by the server the priority number is a <span class="kit-sort-n">2</span> inside the link.

JavaScript

Attributes are enough in most cases. If the rows change after loading (a table filled by a request) call api.refresh(); otherwise Kit.table(table, options) does everything from code and Kit.paginate(table, rows) is the shortcut for pagination only. Both return the same object.

const api = Kit.table("#invoices", { sort: true, size: 10, empty: "No invoices" });

api.sort(3, "descending");   // column (from 0) and direction: "ascending", "descending" or "none"
api.sort([[2, "ascending"], [3, "descending"]]);   // several columns (with data-kit-sort="multi")
api.filter("alfa");          // like typing in the search field
api.page(2);                 // go to page 2; api.page() reads it
api.pageSize(25);            // rows per page; 0 = all
api.refresh();               // after adding, removing or changing rows
api.state();                 // { sort: { column, direction, criteria }, query, page, pages, size, total, count }

document.querySelector("#invoices").addEventListener("kit:page", (e) => {
  console.log(e.detail);     // { page, pages, size, total }
});

Sticky header and columns

By default the headers (<th>) stay stuck under .kit-header while the page scrolls. Inside kit-table-wrap the box scrolls only horizontally, so the header has nothing to detach from. For a long table add kit-table-scroll to the box: it has a maximum height (--kit-table-h, by default 28rem), also scrolls vertically and the header stays attached to its top edge. Cell spacing is adjusted with --kit-row (vertical) and --kit-cell (horizontal).

kit-table-fix on the table locks the first column on the left while scrolling horizontally. It works with CSS only, even on rows added later (for example by htmx), and goes well with highlighted and selected rows. The corner cell (header of the fixed column) stays above everything. Try scrolling the table from one side to the other.
