Labels, help and required fields

A field is a .kit-field: it can be a <label> wrapping the input (as on the Forms: basic fields page) or a <div> with a <label class="kit-label" for="…"> and the input next to it. The second form is needed when there are help text and messages below the field, and for the horizontal layout; it is also the one Django generates. .kit-hint is the help text, linked to the field with aria-describedby.

.kit-required on the label adds the red asterisk; .kit-optional adds "(optional)", which you change with --kit-optional-text. The field's required attribute remains what counts for the browser and the server.

Layout

Column and grid

.kit-form puts the fields in a column with the kit's spacing (--kit-sp). For several fields on the same row there are two ways: .kit-fields (an adaptive grid, kit-field-wide takes two columns) or the 12-column grid with .kit-row and .kit-col-*, as in Bootstrap, to decide the width of each field and where they wrap.

Horizontal

.kit-form-h on the form (or .kit-field-h on a single field) puts the label on the left and the field, help and messages on the right. The label width is --kit-label-w (11rem). Below 576 px the fields go back to a column. It needs the form with <div class="kit-field"> and .kit-label.

11 digits, without the IT prefix.

Inline

.kit-form-inline aligns fields and buttons on one row that wraps by itself: for filters and searches.

Sections and groups

.kit-form-section divides a long form into blocks, with a title and explanation on the left and the fields on the right (from 768 px; below that they stack). To group related fields, or radios, use <fieldset class="kit-fieldset"> with the <legend>: a disabled on the fieldset disables the whole group.

States: valid, invalid, warning

is-valid, is-invalid and is-warning go on the field, or on its .kit-field, and apply to everything it contains: border, focus ring and, for groups, all the parts. aria-invalid="true" counts as is-invalid (and is needed by screen readers). The message is a .kit-feedback with -valid, -invalid or -warning, which can be preceded by an icon. The states also work on select, combobox, file field, drop zone and date range.

For a CSS-only check after the user has touched the field, class="kit-validate" on the form uses :user-invalid: the border turns red (and with kit-validate-ok green) when the HTML rules are not met. It does not write messages: for those there is the validation below.

Validation in the browser

data-kit-validate on a <form> (needs kit.js) checks the fields with the HTML rules you already know (required, type="email", pattern, min, max, minlength…): on submit it marks is-invalid, writes the message into the .kit-feedback-invalid (creating it if missing), links the message to the field with aria-describedby, moves focus to the first error and blocks submission, htmx included. A field turns red on blur only if the user typed in it, and the error disappears as soon as the value is correct. With data-kit-validate="ok" the correct fields get is-valid.

The messages are the browser's (in its language). To write your own: data-kit-msg on the field for any error, or data-kit-msg-required, -type, -pattern, -min, -max, -minlength, -maxlength, -step. It works with the kit's fields: calendar (its min, max and excluded-days rules), select, checkboxes and radios, file.

From JavaScript: Kit.validate(form) runs the same check and returns true or false (options { ok, focus }); Kit.validate.reset(form) clears states and messages (the form's reset does it by itself too). If there are errors the form fires kit:invalid with { fields }, the list of invalid fields. The server has the last word: the errors it sends back are shown with is-invalid and .kit-feedback-invalid written in the HTML, and the kit leaves them as they are.

Sizes

kit-input-sm and kit-input-lg on a field; kit-field-sm|lg on a field with its buttons and selects; kit-form-sm|lg on the whole form; kit-input-group-sm|lg on a group. They change --kit-ctl (the height shared by fields and buttons), so they always stay at the same height. kit-btn-sm is the matching button.

Icons inside fields

.kit-control wraps the field and leaves room for an icon on the left (.kit-control-start) and an icon or a button on the right (.kit-control-end): the field makes room by itself. With is-valid, is-invalid or is-warning on the .kit-control (or on its .kit-field) the result icon appears on the right, drawn by CSS: a check, a cross or an exclamation mark, so with no images. data-kit-password on a button shows and hides the password (aria-pressed and the text for screen readers change by themselves).

Field groups

.kit-input-group joins text (.kit-input-text), icons, fields and buttons into a single block with merged borders. It also works with a native select, a .kit-select, a combobox or a field with a calendar. The states (is-invalid…) color all the parts.

Floating label

.kit-float: the label sits inside the field and, when the field is filled or focused, rises and shrinks. CSS only. The field comes before the label and has placeholder=" " (a space). It works for input, textarea and select. It is not used on fields with the calendar.

Checkboxes, radios and cards

.kit-check works for checkboxes and radios. .kit-check-text adds a line of explanation below; .kit-check-group lays them out in a column and kit-check-inline in a row; .kit-check-card turns them into selectable cards (.kit-check-cards puts them in a grid). Wrap the group in a fieldset with a legend. The is-invalid state marks the border of the radio or card.

Other controls

.kit-input also applies to <textarea> (free height, resizable; kit-textarea-auto makes it grow with the text where the browser allows), to a native <select> (with the arrow drawn by CSS), to type="file" and type="color". .kit-range is for type="range". readonly and disabled have a different background; .kit-input-plain shows a value as text, without a frame. data-kit-count="#id" on a text element writes "n / maxlength" and turns yellow near the limit and red at the limit.

With Django

The class names are the ones Django writes in widgets; the error messages from form.errors go into a .kit-feedback-invalid. A filter or template tag, or a widget with attrs, puts the classes on the field.
